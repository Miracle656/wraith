# Offramp order access

An offramp order carries a bank payout amount, a deposit address and a rate, so
reading one back requires proof of having created it.

## Creating an order

`POST /offramp/orders` returns two values the client must keep:

| Field         | Example                                      | Notes |
| ------------- | -------------------------------------------- | ----- |
| `id`          | `ofr_` + 22 URL-safe characters (128 bits)   | The id to look the order up by. Not the provider's id, which is never returned. |
| `accessToken` | `oft_` + 43 URL-safe characters (256 bits)   | Bearer credential. Shown once; only its SHA-256 is stored. |

The response is sent with `Cache-Control: no-store`.

Send either `amountNGN` or `amountStableCoin`, as a JSON number or a plain decimal
string. Anything else (`"abc"`, a negative or zero amount, `"Infinity"`, a boolean,
an array) is refused with `400` before any lookup or provider call. Each currency
has its own ceiling:

| Variable                          | Default      | Purpose |
| --------------------------------- | ------------ | ------- |
| `OFFRAMP_MAX_AMOUNT_NGN`          | `10000000`   | Largest `amountNGN` accepted. |
| `OFFRAMP_MAX_AMOUNT_STABLECOIN`   | `10000`      | Largest `amountStableCoin` accepted. |

A value that is not a positive number is ignored and the default applies.

## Reading an order

```bash
curl -H "Authorization: Bearer $ACCESS_TOKEN" \
  https://<host>/offramp/orders/$ORDER_ID
```

| Status | Meaning |
| ------ | ------- |
| `200`  | The token belongs to this order. |
| `401`  | No usable `Authorization: Bearer` header. Identical for every id. |
| `404`  | Unknown id, malformed id, or a token that does not belong to the order. These are deliberately indistinguishable. |
| `429`  | Too many failed lookups from this IP. |

Only failed lookups count toward the limit, so polling your own order never
consumes it. Defaults: 10 failures per 15 minutes per IP.

| Variable                       | Default  | Purpose |
| ------------------------------ | -------- | ------- |
| `OFFRAMP_LOOKUP_MAX_FAILURES`  | `10`     | Failed lookups allowed per window. |
| `OFFRAMP_LOOKUP_WINDOW_MS`     | `900000` | Window length. |

## Retrying a creation

Replaying `POST /offramp/orders` with the same `idempotencyKey` and an identical
request returns the same order (`replayed: true`) with the same `id` and a **new**
`accessToken`; the previous token stops working. A replay only counts as identical
when the wallet, the amount, `bankAccount`, `bankCode`, `accountName` and
`refundAddress` all match:

| Replay differs in                     | Result |
| ------------------------------------- | ------ |
| `walletAddress`                       | `409`, and nothing about the order. |
| the amount                            | `409` (different request). |
| bank account, bank code, account name or refund address | `409` (different order details). |

Idempotency keys should therefore be random and generated by the client.

Two simultaneous requests with the same key resolve the same way: one creates the
order, the other is answered as the replay (`200`, `replayed: true`) rather than
with an error, after the same wallet and request checks. Each replay issues a new
token, so the token from the most recent response is the one that works.

The request is compared through a stored HMAC-SHA256 fingerprint keyed with
`LINQ_API_KEY`, not by storing the bank details. Rotating that key means a retry
of an order created before the rotation is refused with `409`.

## Upgrading

- Orders created before this change have no `id` or token and cannot be read
  through `GET /offramp/orders/:orderId`. Replaying their creation request
  (same key and wallet) issues them credentials.
- The lookup response now reports `source: "live"` instead of `"linq"`.
- Two nullable columns were added to `OfframpOrder` (`publicId`,
  `accessTokenHash`); run `npx prisma db push`.
- A third nullable column, `requestHash`, binds an idempotency key to the request
  that created the order (`npx prisma db push` adds it; the server also does so at
  boot). Orders created before it have none and are compared on amount alone.
